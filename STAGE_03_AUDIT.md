# Endemion Life — Stage 03: аудит перед реализацией

Дата: 2026-11-04. Ветка `feature/stage-03` от `main` (`8fdc012`), рабочее дерево чистое. Отчёты Stage 01, 01.5 и 02 сверены с кодом; ниже — то, что есть в коде на самом деле.

## 1. Существующая архитектура

- Монорепозиторий pnpm: `packages/game-core` (чистая логика), `packages/shared` (zod-схемы, `toLifeView`), `packages/database` (Prisma), `packages/ui`, `apps/api` (NestJS), `apps/web` (Next.js).
- `game-core` не знает о базе и сети. `applyAction(state, action)` — чистая функция: состояние + действие + `rngState` → новое состояние и записи истории. Генератор Mulberry32, состояние генератора хранится в сохранении.
- Годовой цикл (`engine/game.ts → advance`): `ageOneYear` (возраст, рост, навыки, путь, доход, смерть от старости) → `worldYearly` + `npcYearly` (тихие изменения и отложенные записи) → запись года → `questYearly`, `consequencesYearly` → `selectEvent`.
- Сохранение: формат 2 (`SAVE_SCHEMA_VERSION = 2`), `migrateSave` переводит 1 → 2, `parseSave` строго проверяет каждое поле. Сервер вызывает `parseSave` при каждом чтении строки `lives`.
- База: `lives.state` (JSON целиком), `life_snapshots` (последние 50 версий), `history_entries` (уникальный `(life_id, seq)`), `game_actions` (уникальный `(life_id, action_id)`, хранит ответ для повтора). Действие — одна транзакция с `SELECT … FOR UPDATE` и проверкой `expectedVersion`.
- Откат (`restore`): новая версия, новое `rngState`, удаление истории и снимков отменённой ветки.
- Клиент получает `LifeView`: без seed, `rngState` и скрытых характеристик (`profile` отдаёт скрытое только после раскрытия).
- Сайт: `GameStore` с облачной и локальной (localStorage) реализацией; локальная включается, если `/api/health` недоступен.

## 2. Что уже реализовано (проверено в коде)

| Область | Где | Состояние |
| --- | --- | --- |
| NPC | `character/npcs.ts` | id `n<число>`, роль относительно персонажа (12 ролей), имя с фамилией, пол, `bornAt` (относительно возраста персонажа), черта, темперамент, занятие (текст), биография, отношение, сила, навык для обучения, `alive`/`diedAt` |
| Жизнь NPC | `character/npc-life.ts` | Только старение, смерть от старости, остывание отношений. Нет браков, детей, карьеры, болезней |

## 3. Чего не хватает для Stage 03

1. Связей NPC между собой по id (родители, супруги, дети) и проверки целостности родства.
2. Жизни NPC по правилам: профессия и карьера в системе профессий Stage 02, образование, сословие, браки и дети в кругу родни, болезни, несчастные случаи, исчезновение, отставка, смерть с причиной.
3. Абсолютного времени: все возрасты NPC считаются от возраста текущего персонажа, поэтому при смене поколения их нужно пересчитать.
4. Продолжения за наследника: выбор, законы наследования мира, перенос рода, новая жизнь.
5. Хроники рода и последствий, которые переживают смерть персонажа.
6. Итогов жизни, оценки и достижений.
7. API для продолжения рода с защитой от повтора.

## 4. Потенциальные конфликты

| Конфликт | Решение |
| --- | --- |
| `bornAt`, `metAt`, `diedAt` относительны возрасту персонажа; у наследника другой ноль отсчёта | При наследовании все времена сдвигаются на `bornAt` наследника; у рода есть `epoch` — год рождения текущего персонажа по счёту рода. Хроника хранит годы рода |
| `parseSave` требует `diedAt ≥ 0`, `metAt ≥ 0` | В формате 3 предки могут умереть до рождения наследника: отрицательные значения разрешаются только в формате 3 |
| Роль NPC — отношение к персонажу, а не связь между людьми | Роль остаётся (на ней держатся все события Stage 01–02), рядом появляются связи `parents`/`spouseId`. При наследовании роли пересчитываются по связям |
| `kill()` стирает отложенные последствия | Последствия для рода хранятся отдельно (`lineage.pending`) и при смерти не стираются |
| Откат умершей жизни после передачи наследнику создал бы второго наследника | Откат такой жизни запрещён (409), у новой жизни уникальный `predecessor_id` |
| Новые броски NPC в основном потоке генератора сдвинут жизнь при том же seed | Жизнь NPC Stage 03 бросает кости в отдельном потоке, производном от `rngState` года: основной поток Stage 02 не трогается, после отката исходы другие |
| Рост JSON: состояние лежит и в `lives.state`, и в каждом из 50 снимков | Лимиты: живых NPC, записей хроники, журнала NPC; хроника хранит ключи и id, а не готовые тексты; умершие дальние родственники уходят в компактный архив |
| Новые виды записей истории (`legacy`) | Старый клиент не используется (сайт выкладывается вместе с API); `kind` — varchar(16), значение помещается |

## 5. Стратегия расширения

**Данные.** NPC, родство, хроника и достижения остаются в `lives.state` (формат 3): они меняются вместе с ходом, откатываются вместе со снимком и проверяются одной функцией `parseSave`. Отдельные таблицы NPC, родства, хроники и достижений не нужны, пока NPC не общие между игроками: у каждой жизни свой срез рода, а наследник получает род целиком при создании. Каждое поколение — отдельная строка `lives` (свои снимки, своя история, свой откат). В `lives` добавляются три столбца: `lineage_id`, `generation`, `predecessor_id` (уникальный) — для списка поколений и защиты от второго наследника. Только добавление; прежний код их не замечает.

**Ядро.** Новые модули без переписывания старых:
- `family/kin.ts` — связи по id, производные родственники (братья, бабушки, внуки, дяди), проверка циклов и возрастов;
- `character/npc-life.ts` — расширение: поведение с весами и условиями, отдельный поток генератора;
- `legacy/{laws,heirs,inherit}.ts` — законы мира, выбор наследника, перенос рода;
- `legacy/chronicle.ts`, `legacy/achievements.ts`, `legacy/summary.ts`;
- `narrative/legacy-events.ts` — сюжеты поколений.

Новое действие `{ type: "succeed", heirId }` идёт через обычный `POST /api/lives/:id/actions`: та же транзакция, та же защита `actionId` и `expectedVersion`. Сервер в той же транзакции создаёт жизнь наследника.

**Интерфейс.** Существующие `Panel`, `Button`, `Tag`, `Meter`, вкладки досье и диалог сохранений. Новые вкладки досье («Род», «Хроника рода», «Достижения»), экран итогов жизни и выбора наследника вместо карточки смерти.

## 6. Риски миграций

| Риск | Мера |
| --- | --- |
| Формат 2 → 3 потеряет данные | Переход только добавляет поля; связи родства выводятся из ролей; тест на 12 сохранениях формата 1 (через 1 → 2 → 3) и на сохранениях формата 2 |
| Выведенные связи нарушат проверку (бабушка младше родителя на 6 лет) | При переводе бабушка или дед привязывается к родителю, только если разница не меньше 14 лет, иначе остаётся без связи |
| SQL-миграция заблокирует таблицу | `ADD COLUMN` с константой по умолчанию и уникальный индекс на пустом столбце; в рабочей базе одна жизнь |
| Откат кода после миграции | Прежний код не читает новые столбцы; жизни формата 3 прежний код не откроет (формат новее игры) — это отражено в ROLLBACK.md: откат кода после первых ходов на формате 3 требует восстановления копии |
| Снимки формата 1 и 2 | Откат к ним проходит через `parseSave` → перевод в формат 3 |

## 7. План тестирования

- **Unit (game-core):** связи и запреты (циклы, ребёнок старше родителя, брак с умершим, дубли), жизнь NPC (взросление, карьера в профессиях мира, образование, браки, дети, усыновление, исчезновение, смерть с причиной, лимиты, детерминированность), законы наследования шести миров, выбор наследника (запреты), перенос рода (роли, времена, имущество, черты), защита от циклов наследования, хроника, сюжеты поколений без повторов, достижения, итоги жизни, перевод сохранений 1 → 3 и 2 → 3, скрытое не утекает.
- **API:** смерть → выбор наследника → новая жизнь, повтор запроса, конфликт версии, второй наследник, откат после передачи, чужая жизнь, хроника в новой жизни, жизни формата 1 и 2 в базе.
- **E2E (Playwright, компьютер и Pixel 7):** итоги жизни, выбор наследника и следующее поколение, древо, хроника рода; переключение языка.
- **Регрессия:** все тесты Stage 01, 01.5, 02; полная жизнь с наследником во всех шести мирах.
