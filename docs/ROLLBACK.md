# Откат

Релизы, выложенные через GitHub Actions, откатываются workflow Deploy (operation `rollback`) или `sh /opt/endemion-life-deploy/rollback.sh` — docs/GITHUB_ACTIONS_DEPLOYMENT.md, «Откат». Правила для миграций и форматов сохранений ниже действуют и там.

```bash
cd /opt/endemion-life
DC="docker compose -f infrastructure/docker-compose.prod.yml --env-file .env"   # + -f …behind-proxy.yml, если используется
```

## Сначала — понять, что сломалось

```bash
$DC ps
$DC logs --since 15m api migrate | grep -E '"level":"(error|warn)"|Error'
```

| Симптом | Действие |
| --- | --- |
| `migrate` завершился с ошибкой, API не стартовал | Код откатить (ниже). База не изменилась или изменилась частично — см. «Миграции» |
| API работает, но с ошибками в новом коде | Откат кода |
| Испорчены данные | Восстановление базы из копии (docs/DATABASE_BACKUPS.md) |
| Сломан только Nginx / сертификат | `$DC logs nginx`, `$DC exec nginx nginx -t`; откат кода затрагивает и конфигурацию Nginx |

## Откат кода (без изменений схемы базы)

```bash
git log --oneline -5                     # найти прежнюю версию (её записывали перед обновлением)
git checkout <прежний коммит>
$DC build api web nginx
$DC up -d
$DC ps
curl -fsS https://life.endemion.online/api/health
```

Вернуться на актуальную ветку после исправления: `git checkout main && git pull --ff-only`.

## Миграции

Prisma не откатывает миграции автоматически. Правило для новых миграций: **сначала расширять, потом сужать** — новый столбец добавляется так, чтобы прежний код продолжал работать; удаление столбцов и таблиц — отдельным обновлением, когда новый код уже в работе. Тогда откат кода не требует отката базы.

Если обновление содержало несовместимую миграцию или миграция упала посередине:

1. Остановить приложение: `$DC stop api web monitor`.
2. Посмотреть состояние: `$DC run --rm migrate node_modules/.bin/prisma migrate status`.
3. Восстановить базу из копии, сделанной перед обновлением (решение владельца: изменения после копии теряются):
   ```bash
   $DC exec backup restore.sh /backups/manual/<копия перед обновлением>.dump
   ```
4. Откатить код (раздел выше) и запустить: `$DC up -d`.

Упавшую миграцию на копии базы можно разобрать отдельно: `restore.sh … --target endemion_life_debug`.

## Stage 03: формат сохранения 3

Миграция `20261104120000_stage03_lineage` только добавляет столбцы `lives.lineage_id`, `lives.generation`, `lives.predecessor_id` и два индекса. Прежний код (Stage 02) их не читает, поэтому сама миграция откат кода не блокирует.

Ограничение: код Stage 02 не открывает сохранения формата 3 («формат новее игры»). Жизнь переходит в формат 3 при первом действии после обновления.

| Когда откатываем | Что делать |
| --- | --- |
| До первого действия игроков на новой версии (`SELECT count(*) FROM lives WHERE schema_version = 3` = 0) | Только откат кода (образы `:pre-stage03`). База не трогается |
| После действий на формате 3 | Откат кода + восстановление копии, снятой перед обновлением (`restore.sh`). Действия после копии теряются — решение владельца |

Проверить перед решением: `$DC exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT schema_version, count(*) FROM lives GROUP BY 1"`.

Удалять новые столбцы при откате не нужно: код Stage 02 с ними работает.

## Stage 04: форматы сохранения 4 и 5, перенос из браузера

Миграция `20261105090000_stage04_import` только добавляет `lives.origin` (`'server'` по умолчанию), `lives.import_id` и уникальный индекс `(player_id, import_id)`. Прежний код их не читает. Удалять их при откате не нужно.

Ограничение то же, что у Stage 03: прежний код не открывает сохранения формата новее своего («формат новее игры»). Текущий формат — 5 (хозяйство и запас товаров рынка). Жизнь переходит в формат 5 при первом действии после обновления. Рабочая среда сейчас на Stage 02 (формат 2): при выкладке Stage 04 сохранения пройдут цепочку 2 → 3 → 4 → 5. Формат 5 не требует миграции базы: запас товаров лежит в `lives.state`.

| Когда откатываем | Что делать |
| --- | --- |
| До первого действия игроков на новой версии (`SELECT count(*) FROM lives WHERE schema_version >= 3` = 0) | Только откат кода на прежние образы. База не трогается |
| После действий на формате 4 | Откат кода + восстановление копии, снятой перед обновлением (`restore.sh`). Действия и перенесённые жизни после копии теряются — решение владельца |

Проверить перед решением: `$DC exec postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT schema_version, origin, count(*) FROM lives GROUP BY 1, 2"`.

Nginx: в `infrastructure/nginx/snippets/app.conf` добавлен `location = /api/lives/import` с `client_max_body_size 2m`. Откат кода Nginx возвращает общий лимит 32 КБ: перенос из браузера перестанет работать (413), остальное — нет.

## Откат восстановления базы

Restore не удаляет прежнюю базу: она остаётся как `<база>_before_<время>`. Возврат — переименованием, docs/DATABASE_BACKUPS.md, раздел «Откат восстановления». Кроме того, есть копия в `pre-restore/`.

## Откат HTTPS / HSTS

- Новый сертификат не работает: `HSTS_MAX_AGE` не трогать; `$DC exec nginx /opt/endemion/nginx-entrypoint.sh reload` после исправления файлов в томе `letsencrypt`.
- HSTS включён, а HTTPS сломан: выключить HSTS нельзя для браузеров, которые его уже запомнили (до `max-age`). Поэтому HSTS включается только после `check-https.sh` и проверки в браузере, а чинить нужно HTTPS.
- Режим behind-proxy: откат блока `life.endemion.online` в Caddyfile — по сохранённой копии файла, затем `caddy reload`.

## После отката

- `sh infrastructure/scripts/check-https.sh https://life.endemion.online`
- `$DC exec backup backup.sh` — свежая копия текущего состояния.
- Запись в журнале изменений: что откатили и почему.
