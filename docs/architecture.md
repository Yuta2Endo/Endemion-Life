# Архитектура Endemion Life (Stage 01, Stage 01.5, Stage 02)

## Состав монорепозитория

| Путь | Назначение |
| --- | --- |
| `packages/game-core` | Игровая логика без ввода-вывода: персонаж, возраст, события, проверки, эффекты, шесть вселенных |
| `packages/shared` | Схемы запросов (zod), представление жизни для клиента (`toLifeView`), общие константы |
| `packages/database` | Схема Prisma, миграции, клиент PostgreSQL через `@prisma/adapter-pg` |
| `packages/ui` | Общие компоненты интерфейса: Button, Panel, Meter, Tag, Ornament |
| `apps/api` | REST API на NestJS: сессии, аккаунты, каталог вселенных, жизни, действия, история, сохранения |
| `apps/web` | Сайт на Next.js: главная, выбор мира, создание персонажа, игровой экран |
| `infrastructure` | Docker Compose для разработки и рабочей среды, Nginx, резервное копирование, монитор, скрипты HTTPS и нагрузочного теста |
| `.github/workflows` | CI (lint, типы, тесты, миграции, E2E, сборка, Docker) и проверки безопасности |

Зависимости идут в одну сторону: `web` и `api` → `shared` → `game-core`. `game-core` не знает ни о базе, ни о сети.

## Сервер — источник истины

Клиент отправляет только намерение: «прожить год» (`advance`), «выбрать вариант» (`choose`) или «пообщаться с человеком» (`interact`, Stage 02). Результат считает сервер функцией `applyAction` из `game-core`:

```
состояние + действие + rngState → новое состояние + записи истории + новый rngState
```

Функция чистая: без времени, без `Math.random`, без обращений к базе. Поэтому одинаковые входные данные всегда дают одинаковый результат, и логику легко тестировать.

### Случайность

Генератор Mulberry32 с seed. Его текущее состояние (`rngState`) хранится в сохранении жизни. Клиент не может повлиять на бросок, а жизнь можно воспроизвести по seed.

## Игровое ядро Stage 02

Каждый мир состоит из двух частей: `universes/<id>.ts` (Stage 01: расы, происхождения, путь силы, события) и `universes/<id>.world.ts` (Stage 02: сословия, шкалы мира, фракции, навыки, таланты, слабости, ремёсла, образование, специализации, тайны рода, отложенные последствия, новые события). `registry.ts` собирает их в один `UniverseDefinition`.

| Модуль | Что делает |
| --- | --- |
| `character/birth.ts` | Рождение: семья по виду происхождения, место, знамение, таланты (часть спит), слабость, потенциал и судьба, тайна рода, биография. Отдельный поток Rng `birth`: броски Stage 01 при том же seed не меняются |
| `character/npcs.ts`, `npc-life.ts`, `interactions.ts` | NPC с именем, возрастом, чертой, занятием и силой; старение и смерть; общение (раз в год с человеком, исход считает сервер) |
| `rpg/` | Общие навыки, ремёсла, таланты, слабости; поиск по миру; влияние талантов на рост, проверки, путь силы, лечение и доход |
| `world/rules.ts`, `world/quests.ts` | Законы мира каждый год: скверна, задания Системы, искажение ци, сердце Дао и карма, угроза Врат, милость двора |
| `narrative/consequences.ts`, `people.ts` | Отложенные последствия (`later`) и общие события семьи, людей, возраста и талантов |
| `engine/profile.ts` | Что видит игрок: биография, люди, шкалы, задание. Скрытое отдаётся только после раскрытия |

Против повторов: событие не приходит, если оно среди 4 последних; без `cooldown` и `maxOccurrences` — не чаще раза в 3 года; вес делится на число прошлых повторов.

Формат сохранения 2. Сохранения формата 1 переводит `migrateV1` в `engine/save.ts` при чтении: ничего не удаляется, недостающее (семья, таланты, сословие, NPC по флагам Stage 01) выводится из seed. Столбец `lives.schema_version` показывает, какие жизни ещё в старом формате.

## Обработка действия (`POST /api/lives/:id/actions`)

1. Тело проверяется схемой `actionRequestSchema`: `actionId` (UUID), `expectedVersion`, `action`.
2. Транзакция PostgreSQL. Строка жизни блокируется `SELECT … FOR UPDATE`: параллельные запросы к одной жизни выполняются по очереди.
3. Если действие с таким `actionId` уже применено (уникальный ключ `(lifeId, actionId)`), возвращается сохранённый результат. Повторная отправка не применяет действие дважды.
4. Если `expectedVersion` не совпадает с текущей версией — `409 VERSION_CONFLICT`. Клиент перезагружает состояние.
5. `applyAction` считает новое состояние. В той же транзакции записываются: новая версия жизни, снимок версии (`LifeSnapshot`), записи истории, запись действия.
6. Хранятся последние 50 снимков (`MAX_SNAPSHOTS`). К любому из них можно вернуться через `POST /api/lives/:id/restore`. Восстановление получает новый номер версии (старые `expectedVersion` клиентов становятся недействительными), а записи истории и снимки после выбранной версии удаляются: прожитая «ветка» отбрасывается.

## Сессии и безопасность

- Сессия — устройство: случайный токен в cookie `el_session` (HttpOnly, SameSite=Lax, Secure в рабочей среде). В таблице `sessions` хранится только SHA-256 токена, срок и отметка отзыва. Гость — игрок без аккаунта; аккаунт (почта и пароль scrypt) привязывается к игроку, гостевые жизни переносятся при входе. Подробно: [AUTHENTICATION.md](AUTHENTICATION.md).
- Защита от подделки запросов: изменяющие запросы принимаются только как `application/json` и только с разрешённого `Origin` (`CORS_ORIGINS`).
- Ограничение частоты запросов через Redis (`RATE_LIMIT_PER_MINUTE`). Если Redis недоступен, API продолжает работать без общего лимита и сообщает об этом в `/api/health`; лимит входа и регистрации (`AUTH_RATE_LIMIT_PER_MINUTE`) переходит на счётчик в памяти.
- Недоступность PostgreSQL — `503 UNAVAILABLE`, после возвращения базы API восстанавливается сам.
- Журналы — JSON с request id и временем ответа, секреты вырезаются ([MONITORING.md](MONITORING.md)).
- Все входные данные проверяются zod-схемами из `packages/shared`. Тело запроса ограничено 16 КБ.
- Helmet, отключён `X-Powered-By`, ошибки отдаются в едином формате `{ error: { code, message, details? } }`.

## Сайт

- Браузер обращается только к своему адресу. В разработке `/api/*` проксирует Next.js (`API_INTERNAL_URL`), в рабочей среде — Nginx. Cookie сессии остаётся first-party.
- Хранилище игры `GameStore` имеет две реализации: облачную (через API) и локальную (localStorage, идентификаторы `local-…`) для работы без сервера.
- Тексты хранятся как `LocalizedText { ru, en }`. Язык выбирается в интерфейсе и запоминается в cookie `el_locale`.

## Рабочая среда

`infrastructure/docker-compose.prod.yml` поднимает:

```
nginx :80/:443 ──/api/*──► api :4000 ──► postgres, redis
               └──/*─────► web :3000
migrate — применяет миграции и завершается; api стартует только после него
certbot — продление сертификата Let's Encrypt
backup  — pg_dump по расписанию с проверкой восстановлением
monitor — проверка /api/health и оповещения
```

Nginx работает в режиме `tls` (свой сертификат) или `behind-proxy` (HTTPS завершает внешний Caddy). Подробно: [DEPLOYMENT.md](DEPLOYMENT.md), [HTTPS_SETUP.md](HTTPS_SETUP.md), [DATABASE_BACKUPS.md](DATABASE_BACKUPS.md).

Образы собираются из корневого `Dockerfile` (цели `api`, `web`, `migrate`). API запускается от пользователя `node`, с одними рабочими зависимостями (`pnpm deploy --prod`). Сайт — автономная сборка Next.js (`output: "standalone"`).
