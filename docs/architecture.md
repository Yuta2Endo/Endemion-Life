# Архитектура Endemion Life (Stage 01, Stage 01.5, Stage 02, Stage 03, Stage 04)

## Состав монорепозитория

| Путь | Назначение |
| --- | --- |
| `packages/game-core` | Игровая логика без ввода-вывода: персонаж, возраст, события, проверки, эффекты, шесть вселенных |
| `packages/shared` | Схемы запросов (zod), представление жизни для клиента (`toLifeView`), общие константы |
| `packages/database` | Схема Prisma, миграции, клиент PostgreSQL через `@prisma/adapter-pg` |
| `packages/ui` | Общие компоненты интерфейса: Button, Panel, Meter, Tag, Ornament |
| `apps/api` | REST API на NestJS: сессии, аккаунты, каталог вселенных, жизни, действия, история, сохранения |
| `apps/web` | Сайт на Next.js: главная, выбор мира, создание персонажа, игровой экран |
| `infrastructure` | Docker Compose для разработки и рабочей среды, Nginx, резервное копирование, монитор, скрипты HTTPS и нагрузочного теста |
| `.github/workflows` | CI (lint, типы, тесты, миграции, E2E, сборка, Docker) и проверки безопасности |

Зависимости идут в одну сторону: `web` и `api` → `shared` → `game-core`. `game-core` не знает ни о базе, ни о сети.

## Сервер — источник истины

Клиент отправляет только намерение: «прожить год» (`advance`), «выбрать вариант» (`choose`) или «пообщаться с человеком» (`interact`, Stage 02). Результат считает сервер функцией `applyAction` из `game-core`:

```
состояние + действие + rngState → новое состояние + записи истории + новый rngState
```

Функция чистая: без времени, без `Math.random`, без обращений к базе. Поэтому одинаковые входные данные всегда дают одинаковый результат, и логику легко тестировать.

### Случайность

Генератор Mulberry32 с seed. Его текущее состояние (`rngState`) хранится в сохранении жизни. Клиент не может повлиять на бросок, а жизнь можно воспроизвести по seed.

## Игровое ядро Stage 02

Каждый мир состоит из двух частей: `universes/<id>.ts` (Stage 01: расы, происхождения, путь силы, события) и `universes/<id>.world.ts` (Stage 02: сословия, шкалы мира, фракции, навыки, таланты, слабости, ремёсла, образование, специализации, тайны рода, отложенные последствия, новые события). `registry.ts` собирает их в один `UniverseDefinition`.

| Модуль | Что делает |
| --- | --- |
| `character/birth.ts` | Рождение: семья по виду происхождения, место, знамение, таланты (часть спит), слабость, потенциал и судьба, тайна рода, биография. Отдельный поток Rng `birth`: броски Stage 01 при том же seed не меняются |
| `character/npcs.ts`, `npc-life.ts`, `interactions.ts` | NPC с именем, возрастом, чертой, занятием и силой; старение и смерть; общение (раз в год с человеком, исход считает сервер) |
| `rpg/` | Общие навыки, ремёсла, таланты, слабости; поиск по миру; влияние талантов на рост, проверки, путь силы, лечение и доход |
| `world/rules.ts`, `world/quests.ts` | Законы мира каждый год: скверна, задания Системы, искажение ци, сердце Дао и карма, угроза Врат, милость двора |
| `narrative/consequences.ts`, `people.ts` | Отложенные последствия (`later`) и общие события семьи, людей, возраста и талантов |
| `engine/profile.ts` | Что видит игрок: биография, люди, шкалы, задание. Скрытое отдаётся только после раскрытия |

Против повторов: событие не приходит, если оно среди 4 последних; без `cooldown` и `maxOccurrences` — не чаще раза в 3 года; вес делится на число прошлых повторов.

Формат сохранения 2. Сохранения формата 1 переводит `migrateV1` в `engine/save.ts` при чтении: ничего не удаляется, недостающее (семья, таланты, сословие, NPC по флагам Stage 01) выводится из seed. Столбец `lives.schema_version` показывает, какие жизни ещё в старом формате.

## Род и поколения (Stage 03)

Каждое поколение — отдельная жизнь (строка `lives`, свои снимки, история и откат). Род целиком лежит в состоянии жизни (`state.lineage`) и при наследовании переходит в новую жизнь. Отдельных таблиц NPC, родства, хроники и достижений нет: NPC не общие между игроками, у каждой жизни свой срез рода, а откат должен откатывать всё вместе.

| Модуль | Что делает |
| --- | --- |
| `family/kin.ts` | Родство по id: хранятся только родители (`parents`) и супруги (`spouseId`, `formerSpouses`). Братья, бабушки, внуки, дяди, двоюродные вычисляются `KinGraph`. `kinProblem` запрещает циклы, родителя моложе ребёнка на 12 лет, брак с умершим, невзаимный брак, повторы, больше двух родителей |
| `family/events.ts` | Смерть, брак, развод, рождение, исчезновение и возвращение NPC; раздел наследства умершего NPC по закону мира; архив забытых умерших |
| `character/npc-life.ts` | Жизнь NPC: правила Stage 02 (старость, остывание отношений) из основного генератора, собственная жизнь — из отдельного потока `seed + rngState` года. 18 видов поведения с условиями и весами (учёба, работа, карьера, наставничество, сословие, брак, дети, усыновление, развод, болезнь, несчастный случай, бой, тренировка, исчезновение, отставка). Событие с NPC — в среднем раз в пять лет |
| `legacy/laws.ts` | Законы наследования шести миров: порядок (старший, достойнейший, поровну, по завещанию), возраст самостоятельности, опека, доли, сбор, наследуемые сословия, кровь (корень духа, пробуждение) |
| `legacy/succession.ts` | `heirCandidates` и `succeed`: наследник становится персонажем, умерший — записью NPC (`lifeGen`), все времена сдвигаются на год рождения наследника, род переходит целиком |
| `legacy/stories.ts`, `lineage.ts` | 16 сюжетов поколений и 4 последствия для рода (`kind: "legacy"`, `lineageMax`), нити рода, последствия для рода (`lineage.pending` — не стираются со смертью) |
| `legacy/achievements.ts`, `summary.ts` | 30 достижений (одно на род), оценка жизни из шести частей, деньги в неё не входят |
| `legacy/present.ts` | Представление для клиента: итоги, наследники, наследство, хроника рода, древо |

Лимиты размера сохранения: живых NPC — 40 (новые семьи у родни не заводятся), всего NPC — 90 (умершие без связей уходят в архив, имя остаётся в `lineage.names`), хроника рода — 400 записей (рядовые уходят в архив по счётчику, начало рода, наследования и достижения не архивируются), журнал NPC — 12 записей, ключевых решений — 12. Хроника хранит вид записи и значения, а текст собирается при показе.

### Продолжение рода (`POST /api/lives/:id/succession`)

Тело: `{ actionId, expectedVersion, heirId }`. Клиент называет только наследника.

1. Транзакция и блокировка строки жизни, как у действия.
2. Повтор с тем же `actionId` возвращает ту же новую жизнь (`replayed: true`); тот же `actionId` с другим наследником — `409 ACTION_ID_REUSED`.
3. Проверки сервера: жизнь закончена (`LIFE_NOT_ENDED`), род ещё не продолжен (`LINEAGE_CONTINUED`), наследник живой, кровный и подходит по закону мира (`HEIR_LOCKED`), версия (`VERSION_CONFLICT`), лимит живых жизней.
4. `succeed(state, heirId, salt)`: `salt` — случайный UUID сервера, поэтому seed наследника нельзя вычислить из сохранения предка.
5. В одной транзакции: жизнь умершего получает новую версию с отметкой `continuedBy` и снимок, создаётся жизнь наследника (`lineage_id`, `generation`, `predecessor_id`), записываются её история и снимок, записывается действие `succeed`.
6. Уникальный `lives.predecessor_id` не даёт создать второго наследника даже при гонке. Откат продолженной жизни запрещён (`409 LINEAGE_CONTINUED`).

`GET /api/lives/:id/lineage` — хроника рода (последние 300 записей), древо, достижения, фамильные черты и нити. В ответы на действия хроника рода не входит; в `LifeView.legacy` — только краткие сведения, наследство и (после смерти) итоги жизни с наследниками.

Формат сохранения 3. Перевод 2 → 3 (`migrateV2`) ничего не удаляет: NPC получают поля собственной жизни из потока по id NPC, родство выводится из ролей, появляется род с записью об основании, законченная жизнь получает итог и может быть продолжена.

Усыновление (уточнено в Stage 03.1): приёмный ребёнок — родня по закону (наследует имущество, стоит в очереди наследования, под запретом брака, сословие — по `law.adoptedClass`), но не по крови. `KinGraph.isNatural` считает родство без усыновлений на пути; флаги крови, фамильные таланты и слабости, потенциал и уклон характеристик получает только кровный наследник.

## Хозяйство и общество (Stage 04)

| Модуль | Что делает |
| --- | --- |
| `economy/economy.ts` | Доходы и расходы года — шаг годового цикла вместо прежнего `life/income.ts` (та же формула заработка): ремесло, гильдия, подработка, доход сословия, мотовство, доход мира, состояние хозяйства, налог мира, стоимость жизни по ступени сословия. Нехватка копится в `economy.hardship`, с третьего года подряд — −1 репутации в год. Итоги последнего года и до 10 прошлых лет |
| `economy/worlds.ts` | Конфигурация шести миров: налог и его название, множитель стоимости жизни, названия спада и подъёма, доход мира (зачистки Врат в Нео-Сеуле перенесены сюда из `world/rules.ts`) |
| `narrative/economy-events.ts` | 8 общих событий хозяйства и общества и события миров (подключаются только к своему миру в `universes/registry.ts`). Новые условия: `wealth` с верхней границей, `hardship`, `cycle` |
| `engine/import.ts` | Подготовка жизни из браузера к серверу (`prepareImport`), см. ниже |
| `economy/market.ts` | Рынок мира: по три товара (навык, шкала мира или фракция), цена от состояния хозяйства, наценка 1.25 и скидка 0.8 — покупка всегда дороже продажи. Действие `trade` без хода времени и без генератора; запас до 20 штук, тратится по одной в год, только если даёт эффект |

- **Предел золота** `WEALTH_MAX` = 1 000 000 000 во всех источниках: эффект `wealth`, наследство NPC, конец опеки, наследование, проверка сохранения. Ниже нуля золото не уходит.
- **Состояние хозяйства** (спад, обычные годы, подъём: ×0.8 / ×1 / ×1.2 к заработку) бросается из потока `seed::economy::rngState`; основной генератор новых чисел не тянет.
- **Наследник** продолжает цикл мира, но не наследует нехватку и прошлые счета.
- Формат сохранения 4. Перевод 3 → 4 (`migrateV3`) только добавляет `economy` с нейтральными значениями и не трогает `rngState`.
- Формат сохранения 5. Перевод 4 → 5 (`migrateV4`) добавляет пустой запас товаров `economy.goods`; `parseSave` пропускает только товары мира этой жизни, от 1 до 20 штук.
- Действие рынка `{ type: "trade", goodId, side, qty }` идёт через `POST /api/lives/:id/actions`; клиент называет товар, сторону и количество (1–5), цену и остаток считает сервер. `LifeView.market` — товары, цены, запас и причина, если рынок закрыт (до 16 лет, событие ждёт ответа, жизнь окончена).
- Клиент получает `LifeView.economy` (`presentEconomy`): статьи года с названиями на двух языках, налог, стоимость жизни, состояние мира, нехватка. Без seed и генератора.

### Детерминированность (уточнено в Stage 03.1)

Одинаковое сохранение и действия дают одинаковый результат. Жизнь NPC и хозяйство не берут числа из основного потока. Совпадение будущих событий с прошлой версией игры на том же seed не гарантируется: в пуле новые события, а изменение числа живых NPC меняет число бросков правил Stage 02. Подробно — `STAGE_03_1_AUDIT.md`, раздел 5.

## Перенос жизни из браузера (`POST /api/lives/import`)

Тело: `{ importId, state, history }`, схема `importLifeSchema` (`z.strictObject`, история до 2000 записей со строгой формой). Лимит тела — 2 МБ только на этом маршруте (API и Nginx), остальные запросы — 16 КБ.

1. `prepareImport` (game-core): `parseSave` с переводом старых форматов; продолженная жизнь отклоняется (`LINEAGE_CONTINUED`); новый seed и генератор из соли сервера; нераскрытые потенциал, судьба и спящие таланты бросаются заново; невозможные значения срезаются (золото и уровень не по возрасту, опыт, запасы, путь силы раньше срока, золото NPC, удержанное опекуном) и перечисляются в ответе; несуществующее событие не остаётся ждать ответа.
2. Номера записей истории идут по порядку и раньше записи о переносе (`kind: "import"`).
3. Транзакция: жизнь (`origin = 'local-import'`, `import_id`), история, снимок. Лимит живых жизней действует.
4. Повтор: уникальный `(player_id, import_id)`. Повтор и одновременные запросы возвращают ту же жизнь (`replayed: true`, `adjustments: null`).

Прошлые исходы перенесённой жизни проверить нельзя — поэтому столбец `origin` остаётся у неё навсегда.

**Сайт.** Локальный режим остаётся. Неудачная проверка `/api/health` не запоминается, перед созданием жизни связь проверяется ещё раз. На экране локальной жизни — предупреждение и кнопка «Перенести на сервер»; ключ переноса хранится в записи браузера; запись помечается перенесённой только после ответа сервера и больше не принимает ходов (`MOVED`), старая ссылка ведёт к жизни на сервере. Список жизней находит записи и по ключам localStorage, если индекс потерян между вкладками; локальные жизни помечены «в браузере».

## Обработка действия (`POST /api/lives/:id/actions`)

1. Тело проверяется схемой `actionRequestSchema`: `actionId` (UUID), `expectedVersion`, `action`.
2. Транзакция PostgreSQL. Строка жизни блокируется `SELECT … FOR UPDATE`: параллельные запросы к одной жизни выполняются по очереди.
3. Если действие с таким `actionId` уже применено (уникальный ключ `(lifeId, actionId)`), возвращается сохранённый результат. Повторная отправка не применяет действие дважды. Сохранённое действие сравнивается с повтором без учёта порядка ключей: PostgreSQL хранит `jsonb` с переупорядоченными ключами (исправлено в Stage 04).
4. Если `expectedVersion` не совпадает с текущей версией — `409 VERSION_CONFLICT`. Клиент перезагружает состояние.
5. `applyAction` считает новое состояние. В той же транзакции записываются: новая версия жизни, снимок версии (`LifeSnapshot`), записи истории, запись действия.
6. Хранятся последние 50 снимков (`MAX_SNAPSHOTS`). К любому из них можно вернуться через `POST /api/lives/:id/restore`. Восстановление получает новый номер версии (старые `expectedVersion` клиентов становятся недействительными), а записи истории и снимки после выбранной версии удаляются: прожитая «ветка» отбрасывается.

## Сессии и безопасность

- Сессия — устройство: случайный токен в cookie `el_session` (HttpOnly, SameSite=Lax, Secure в рабочей среде). В таблице `sessions` хранится только SHA-256 токена, срок и отметка отзыва. Гость — игрок без аккаунта; аккаунт (почта и пароль scrypt) привязывается к игроку, гостевые жизни переносятся при входе. Подробно: [AUTHENTICATION.md](AUTHENTICATION.md).
- Защита от подделки запросов: изменяющие запросы принимаются только как `application/json` и только с разрешённого `Origin` (`CORS_ORIGINS`).
- Ограничение частоты запросов через Redis (`RATE_LIMIT_PER_MINUTE`). Если Redis недоступен, API продолжает работать без общего лимита и сообщает об этом в `/api/health`; лимит входа и регистрации (`AUTH_RATE_LIMIT_PER_MINUTE`) переходит на счётчик в памяти.
- Недоступность PostgreSQL — `503 UNAVAILABLE`, после возвращения базы API восстанавливается сам.
- Журналы — JSON с request id и временем ответа, секреты вырезаются ([MONITORING.md](MONITORING.md)).
- Все входные данные проверяются zod-схемами из `packages/shared`. Тело запроса ограничено 16 КБ; исключение — перенос жизни из браузера, 2 МБ (Stage 04).
- Helmet, отключён `X-Powered-By`, ошибки отдаются в едином формате `{ error: { code, message, details? } }`.

## Сайт

- Браузер обращается только к своему адресу. В разработке `/api/*` проксирует Next.js (`API_INTERNAL_URL`), в рабочей среде — Nginx. Cookie сессии остаётся first-party.
- Хранилище игры `GameStore` имеет две реализации: облачную (через API) и локальную (localStorage, идентификаторы `local-…`) для работы без сервера. Локальную жизнь можно перенести на сервер (Stage 04, раздел выше); в локальном режиме исходы по-прежнему считает браузер.
- Тексты хранятся как `LocalizedText { ru, en }`. Язык выбирается в интерфейсе и запоминается в cookie `el_locale`.

## Рабочая среда

`infrastructure/docker-compose.prod.yml` поднимает:

```
nginx :80/:443 ──/api/*──► api :4000 ──► postgres, redis
               └──/*─────► web :3000
migrate — применяет миграции и завершается; api стартует только после него
certbot — продление сертификата Let's Encrypt
backup  — pg_dump по расписанию с проверкой восстановлением
monitor — проверка /api/health и оповещения
```

Nginx работает в режиме `tls` (свой сертификат) или `behind-proxy` (HTTPS завершает внешний Caddy). Подробно: [DEPLOYMENT.md](DEPLOYMENT.md), [HTTPS_SETUP.md](HTTPS_SETUP.md), [DATABASE_BACKUPS.md](DATABASE_BACKUPS.md).

Образы собираются из корневого `Dockerfile` (цели `api`, `web`, `migrate`). API запускается от пользователя `node`, с одними рабочими зависимостями (`pnpm deploy --prod`). Сайт — автономная сборка Next.js (`output: "standalone"`).
