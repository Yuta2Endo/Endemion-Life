# Нагрузочное тестирование и надёжность

Дата: 2026-11-03. Окружение: Windows 11, Docker Desktop (WSL 2), 16 ГБ памяти; стек `infrastructure/docker-compose.prod.yml` из образов этого репозитория (Node 24, PostgreSQL 18, Redis 8). **Это не сервер:** на VPS цифры будут другими, тест нужно повторить там до открытия сайта.

## Нагрузочный тест

Скрипт: `infrastructure/scripts/load-test.mjs` (без сторонних зависимостей). Каждый виртуальный игрок получает свою сессию, создаёт жизнь и играет без пауз: ход; каждый 5-й ход — чтение жизни; каждый 10-й — история (50 записей). Закончившаяся жизнь заменяется новой.

Запуск: 50 игроков, 60 секунд, напрямую в API внутри сети Docker (`http://api:4000`, без Nginx), `RATE_LIMIT_PER_MINUTE=0` — иначе измерялся бы лимит.

```bash
docker run --rm --network <сеть стека> -v "$PWD/infrastructure/scripts:/scripts:ro" \
  -e BASE_URL=http://api:4000 -e ORIGIN=https://<домен> -e USERS=50 -e DURATION=60 \
  --entrypoint node <образ api> /scripts/load-test.mjs
```

| Создание жизни | 124 | 2 | 173.6 | 410.2 | 414.8 | 417.5 | 201 × 124 |

Всего 21 188 запросов за 60.2 с (352 в секунду), **ошибок сервера и сети: 0**.

Ресурсы в середине теста: API 102 % CPU (одно ядро), 393 МБ; PostgreSQL 64 % CPU, 89 МБ; Redis 3 % CPU, 8 МБ.

### Целостность после теста

Запрос по всем 129 жизням и 16 713 действиям в базе:

| Проверка | Нарушений |
| --- | ---: |
| Версия жизни = 1 + число принятых действий (нет потерянных и дублированных ходов) | 0 |
| У текущей версии есть снимок | 0 |
| Версия в сохранённом состоянии = версия строки | 0 |
| Снимков на жизнь не больше 50 | максимум 50 |

### Выводы

- Узкое место — один процесс Node.js API (упирается в одно ядро). База загружена на две трети ядра. Время ответа растёт из-за очереди к процессу, не из-за блокировок.
- 50 игроков без пауз — это примерно 270 ходов в секунду. Живой игрок делает ход раз в несколько секунд, так что такой запас соответствует сотням одновременных игроков. Подтвердить это можно только тестом на сервере.
- Следующий шаг масштабирования (не сделан, не требовался): несколько копий API за Nginx. API не хранит состояние в памяти, кроме резервного счётчика лимита входа на случай недоступности Redis.

| Сценарий | Проверка | Результат |
| --- | --- | --- |
| 10 одновременных ходов с одной версией по одной жизни | Ровно 1 × 200, 9 × `409 VERSION_CONFLICT`, версия +1, целостность | OK |
| Один `actionId` 8 раз одновременно | Все 200, применён один раз (`replayed: false` у одного), одна запись действия | OK |
| 20 игроков × 5 ходов параллельно | Все 200, у каждой жизни 5 действий, целостность | OK |
| Сбой посреди транзакции (запись истории нарушает уникальность после обновления жизни) | 500 без подробностей; версия, возраст, состояние, действия, снимки не изменились; повтор с тем же `actionId` после устранения причины проходит | OK |

### Найдено и исправлено

- Запрос, пришедший во время остановки API, получал `500` «Cannot use a pool after calling end on the pool»: пул PostgreSQL закрывался в `onModuleDestroy`, до остановки HTTP-сервера. Теперь Prisma и Redis закрываются в `onApplicationShutdown` — после него. Повторная проверка под нагрузкой: 0 таких ошибок.
- Недоступность базы отдавалась как `500 INTERNAL` со стеком в журнале на каждый запрос. Теперь — `503 UNAVAILABLE` и одна короткая строка `warn` на запрос, без отправки в Sentry.
